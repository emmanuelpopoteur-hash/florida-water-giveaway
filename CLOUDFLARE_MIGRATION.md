# Legacy Water USA Cloudflare migration

This branch is staging only. Keep the current production domains and lead form active until the D1 test below succeeds.

## Target setup

1. Create a Cloudflare Pages project connected to `emmanuelpopoteur-hash/florida-water-giveaway` and this staging branch. Root directory: repository root. Build command: `node scripts/build-cloudflare.mjs`. Build output directory: `dist`. The `functions` directory stays at the project root, outside `dist`.
2. Staging is deployed at `https://legacy-water-staging.pages.dev/` on this branch with D1 database `legacy-water-leads-staging`. Its `water_test_leads` table and index from `schema.sql` were verified, and a disposable lead returned HTTP 201 with `saved: true` and was read back directly from D1. Keep test leads in staging. Before public cutover, create a separate production D1 database `legacy-water-leads`, apply `schema.sql`, and bind it to the production Pages project.
3. In staging Pages Settings > Bindings, `DB` points to `legacy-water-leads-staging` for Preview and Production of the **staging project**. On the separate public Pages project, bind `DB` to `legacy-water-leads` for its Production environment; keep Preview bound to staging or another disposable database. Redeploy after changing bindings. Never put credentials or lead data in GitHub.
4. In the preview homepage, search ZIP `34771`, choose the provider shown on a bill, then follow the request button. The `/check/` form should prefill `34771` without advancing automatically. Submit a disposable test lead with a day and time, a clearly marked test name, and a phone number authorized for testing. Confirm the page shows success only after the API returns `201 {saved:true,id}`. A retry of the exact same request ID returns `200 {saved:true,id}` without a second row; a changed request using that ID returns `409`.
5. In the D1 Console, query `SELECT id,created_at,zip,preferred_day,preferred_time,full_name,phone,source,campaign,product_interest FROM water_test_leads ORDER BY created_at DESC LIMIT 10;` and match the returned id. Remove the disposable row after verification if desired.
6. Test invalid ZIP, missing binding, and readback failure paths. They must never show success. Check mobile and both languages.
7. Do **not** merge while the apex domain still serves GitHub Pages: the main-branch CTAs would point to `/check/` there, but GitHub Pages cannot run `/api/leads`. Keep the public Pages project's production branch on `cloudflare-migration` and its production `DB` bound to `legacy-water-leads` for the cutover. After those checks, change domain routing while the PR stays draft. `legacywaterusa.com` is registered with Squarespace; registration can stay there. Cloudflare Pages requires the apex domain to be a Cloudflare DNS zone with its nameservers set to Cloudflare at Squarespace. Before any nameserver change, inventory and recreate the existing website, email, verification, and subdomain DNS records in Cloudflare, and confirm the Pages custom domain is configured. A subdomain such as `www.legacywaterusa.com` can instead use a CNAME in Squarespace DNS to the Pages project without moving nameservers, after that subdomain has been associated with Pages. Test the public Pages URL and production D1 write/readback before either DNS path. Once `legacywaterusa.com` actually serves the Cloudflare Pages deployment and `/check/` works on the real domain, merge the PR, switch the public Pages project's production branch to `main`, redeploy, and verify the real domain again. Main stays on the existing live flow until that point. Preserve existing leads in Netlify Blobs with a separate export/retention plan; this change does not migrate historical leads.
